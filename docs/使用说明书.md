## 1. 先确认在哪里修改

**建议今后统一在下面这个已连接 GitHub 的目录里写作和发布：**

```text
D:/Projects/jingxiaoshao-jekyll-site
```

此目录已接入原有 Git 历史和远程仓库，今后直接在这里编辑、提交和推送。C 盘的 `github-first-push` 是迁移前工作副本，不再作为日常写作目录；两处不会自动同步。

日常流程：同步最新内容 → 写 Markdown、放图片 → 查看修改 → 提交 → 推送 → 等待部署 → 打开网站检查。

“提交”是把修改保存成一个版本；“推送”才是把本地版本发送到 GitHub。只在本地提交，网站不会更新。

## 3. 添加一篇文章

在 `_posts/` 新建 `2026-10-17-autumn-reading.md`，复制下面模板，再替换内容和日期：

```markdown
---
title: "秋日阅读小记"
date: 2026-10-17 10:00:00 +0800
category: 阅读笔记
tags: [阅读, 随笔]
description: "用一两句话介绍这篇文章，让列表保持简洁。"
excerpt: "用一两句话介绍这篇文章，让订阅摘要保持简洁。"
---

这里是文章的开头。

## 为什么读这本书

这里写正文。段落之间空一行。

## 我记住的三句话

- 第一条想法。
- 第二条想法。
- 第三条想法。

### 补充说明

这里写更细的内容。
```

文件开头的两行 `---` 包住文章资料，必须保留；不要在它前面添加正文。`title` 是网页标题，文件名日期和 `date` 建议一致；使用实际发布日期，未来时间的文章默认不会显示，到了日期也需要重新构建才能上线。`description` 是简短介绍，`excerpt` 是订阅摘要，建议控制在一两句话。

正文从 `##` 开始分节，不再写一个 `#` 大标题；网页已自动显示文章标题。章节标题会用于阅读目录。文章发布后会自动进入文章列表，不必手动修改首页。

上面的文章地址为：`https://chrunge.github.io/blog/autumn-reading/`。文件名日期后面的部分决定默认网址；文章发布后尽量不要改文件名，以免原链接失效。

### 插入图片

先把图片放入 `assets/images/uploads/autumn-lake.jpg`，再在正文中写：

```markdown
![秋天的湖面]({{ '/assets/images/uploads/autumn-lake.jpg' | relative_url }})
```

不能使用 `D:\照片\图片.jpg` 之类电脑路径。网站上的路径大小写必须与文件名完全一致；图片也要一起提交。

### 常用 Markdown

```markdown
**加粗文字**

> 引用的一段话。

[链接名称](https://example.com)

1. 第一项
2. 第二项
```

## 4. 添加和更新小说

在 `_novels/` 新建 `cloud-journey.md`：

```markdown
---
title: "云海远行"
status: "连载中 · 更新至第二章"
author: "云海小鲸"
cover: /assets/images/novels/cloud-journey-cover.jpg
synopsis: "一只小鲸离开熟悉的云朵，寻找海的尽头。"
---

## 第一章 · 出发

这里写第一章正文。

## 第二章 · 风的来信

这里写第二章正文。
```

把真实封面放到 `cover` 对应位置。暂时没有封面，可以删掉整行 `cover`，作品列表会使用默认图片。不要保留一个实际不存在的图片路径。

当前结构是**一个 Markdown 文件对应一个小说阅读页面**，二级标题对应页面内章节目录。更新时，在同一个文件末尾添加 `## 第三章` 和正文，并修改 `status`，提交即可。

作品会自动出现在“作品”页，网址为 `https://chrunge.github.io/novels/cloud-journey/`。当前没有自动生成的分章独立页面、上一章／下一章导航。如果将长篇拆成多个文件，它们会成为多个独立作品；可以先按卷拆分，并在正文中手动添加相互链接。

## 5. 添加漫画或画集

先准备图片，例如：

```text
assets/images/manga/cloud-journey/ch01/
  cover.jpg
  001.jpg
  002.jpg
  003.jpg
```

再在 `_manga/` 新建 `cloud-journey-ch01.md`：

```markdown
---
title: "云海远行 · 第一话"
status: "已完结 · 3 页"
cover: /assets/images/manga/cloud-journey/ch01/cover.jpg
synopsis: "故事从一封飘来的信开始。"
pages:
  - /assets/images/manga/cloud-journey/ch01/001.jpg
  - /assets/images/manga/cloud-journey/ch01/002.jpg
  - /assets/images/manga/cloud-journey/ch01/003.jpg
---

这里可以写创作说明，也可以留空。
```

`pages` 的排列顺序就是阅读顺序，不会自动扫描图片目录。新增一页时，既要上传图片，也要在 `pages` 中增加一行。`status` 的页数是手动填写的，记得同步更新。

每个图片项前面使用两个空格再加 `- `，不要用 Tab。`cover` 是作品列表封面；如果也希望它出现在漫画阅读中，要把它另列进 `pages`。

作品网址为 `https://chrunge.github.io/manga/cloud-journey-ch01/`，读者可以连续看图或切换逐页。多话漫画可以每话建一个文件，当前不会自动合并成系列目录。

建议使用 JPG、PNG 或 WebP；先缩小过大的原图、压缩到适合网页阅读的体积，再提交。照片类优先 JPG/WebP，透明图使用 PNG/WebP。单文件超过 GitHub 的 100 MiB 限制不能正常推送；漫画应远小于这个体积。

## 6. 手动提交方式一：直接使用 GitHub 网页

适合偶尔改文章，不需要安装 Git。

1. 登录 GitHub，打开源码仓库，确认左上角分支为 `master`。
2. 新建内容：使用 **Add file → Create new file**，在文件名栏输入完整路径，例如 `_posts/2026-10-17-autumn-reading.md`。
3. 粘贴模板，填写正文。已有内容则打开对应文件，点击铅笔图标编辑。
4. 点击 **Commit changes**，填写说明，例如“新增：秋日阅读小记”；选择直接提交到 `master`，确认提交。
5. 图片使用 **Add file → Upload files** 上传到对应图片目录。确保文件确实位于 Markdown 中引用的路径下。
6. 查看仓库 **Actions**，等待最新的 `Build and deploy Cloud Whale` 成功，再打开网站检查。

网页提交会直接上传到远程，不需要再按 Push。图片多时更推荐下一种方式，可以把图片和正文一起提交，避免两次提交之间短暂缺图。GitHub 的 Markdown 预览不是网站最终排版，模板图片可能不会在这里正确预览。

## 7. 手动提交方式二：GitHub Desktop（推荐）

### 首次设置

1. 安装并打开 GitHub Desktop，登录有该仓库写权限的 GitHub 账号。
2. 选择 **File → Add local repository**，添加本说明第 1 节的 D 盘正式目录。
3. 确认仓库是 `Chrunge.github.io`、当前分支是 `master`。
4. 如果添加已有目录遇到权限或所有权错误，可以使用 **File → Clone repository → URL**，输入 `https://github.com/Chrunge/Chrunge.github.io.git`，克隆到一个新的空目录，例如 `D:/Projects/cloud-whale-blog`；以后统一在这个新目录写作。不要克隆到已有文件的博客目录内。

### 每次更新

1. 写作前点击 **Fetch origin**；出现 **Pull origin** 时点击它，同步线上修改。
2. 在当前仓库目录中添加或编辑 Markdown，放好图片。
3. 回到 Desktop 的 **Changes**，查看变动文件，确认只有本次要发布的内容。
4. 在 **Summary** 填写说明，例如“更新：云海远行第三章”。
5. 点击 **Commit to master**，再点击 **Push origin**。
6. 打开 GitHub 的 Actions，确认最新部署成功。

不要把私人草稿、账号密码、完整工作文件夹当作配图一起提交。这个仓库是公开的；`published: false` 只影响网页显示，不能隐藏已经提交到公开仓库的源文件。

## 8. 手动提交方式三：PowerShell 命令行

### 首次准备

本次首次发布通过已连接的 GitHub 账号完成，**不代表本机命令行 Git 已登录**。第一次自己推送时，可能需要在浏览器中登录授权。若登录失败，使用上面的 GitHub Desktop 完成登录；不要把 GitHub 密码或访问令牌写进文章或仓库文件。

打开 PowerShell，进入发布目录：

```powershell
Set-Location 'D:/Projects/jingxiaoshao-jekyll-site'
git remote -v
git branch --show-current
git status
```

确认远程为 `https://github.com/Chrunge/Chrunge.github.io.git`、分支为 `master`。如果你另行克隆过，请改为自己的新目录。

首次提交如提示没有作者信息，在这个仓库内设置一次（把示例改成自己的信息）：

```powershell
git config user.name "你的 GitHub 用户名"
git config user.email "你的 GitHub 提交邮箱"
```

邮箱可从 GitHub **Settings → Emails** 获取自己的隐私邮箱，以避免公开真实邮箱。

### 每次发布

先同步，再开始写作；此时应没有未提交的修改：

```powershell
git pull --ff-only origin master
```

写完后，以一篇带图文章为例，执行（路径替换为本次真实文件名）：

```powershell
git status
git diff
git add -- _posts/2026-10-17-autumn-reading.md assets/images/uploads/autumn-lake.jpg
git diff --cached --stat
git diff --cached
git commit -m "新增：秋日阅读小记"
git push origin master
```

小说则添加 `_novels/你的文件.md` 和封面；漫画则添加 `_manga/你的文件.md` 及对应图片目录。`git diff` 不显示未跟踪文件正文，新文件请在编辑器中查看，添加暂存后也可用 `git diff --cached` 检查。只添加本次想发布的文件；不要未经检查就批量提交所有文件。

如果 `pull` 或 `push` 提示分支冲突、远程有新提交，先保留本地内容并检查差异，使用 Desktop 处理或寻求帮助，不要直接强制推送。`git commit` 显示“nothing to commit”可能是修改尚未保存，或者你修改的是另一个目录。

## 9. 查看是否上线成功

打开：https://github.com/Chrunge/Chrunge.github.io/actions

找到与本次提交说明对应的 **Build and deploy Cloud Whale**：

- 排队或运行中：等待完成，通常需要几分钟。
- 绿色成功：打开首页和刚修改的具体页面，检查文字、图片和链接。
- 红色失败：打开任务，查看失败步骤的日志，修正后再次提交；失败时不要认为新内容已经上线。

工作流会检查脚本、构建页面、校验链接和图片，并部署网站。若页面仍显示旧内容，可强制刷新或打开无痕窗口，同时核对 Actions 对应的提交是否为最新。

仓库 **Settings → Pages → Build and deployment → Source** 推荐使用 **GitHub Actions**。首次发布时仓库还触发了一个系统的 `pages build and deployment` 任务，两项均成功；若后续仍看到两套部署任务，请检查这里是否仍为分支发布模式，并切换为 GitHub Actions，保留项目自己的工作流。

## 10. 本地预览（可选）

当前电脑的 Ruby 依赖安装曾因缺少本机编译工具而失败，因此不能假设下面命令已经可以直接使用。GitHub 上的正式 Jekyll 构建已经通过；你可以先使用网页或 Desktop 发布，不必先解决本地预览环境。

如需正式本地预览，安装带开发工具的 Ruby 3.3 环境，完成开发工具安装后，在仓库目录执行：

```powershell
bundle install
bundle exec jekyll serve --host 127.0.0.1
```

打开 `http://127.0.0.1:4000`，结束时按 `Ctrl+C`。不要直接双击源文件 `index.html`。此前 `.preview/site` 是辅助预览产物，内容不会随着源文件编辑自动更新，不能作为最新发布结果。

如已安装 Python，还可执行：

```powershell
bundle exec jekyll build
python scripts/check_site.py _site
```

## 11. 常见问题和维护边界

| 问题 | 优先检查 |
| --- | --- |
| 新文章没出现 | 是否放在 `_posts`；文件名有日期；日期是否在未来；是否推送；部署是否成功 |
| 小说或漫画没出现 | 是否放在 `_novels` / `_manga`；开头两行 `---` 是否齐全 |
| 图片或封面破图 | 图片是否提交；路径大小写是否一致；是否误写了本地磁盘路径 |
| YAML 解析失败 | 使用空格缩进；标题等文字加英文双引号；文字中的双引号需转义或换一种引号 |
| 小说没有新章节 | 是否保存并推送；新增章标题是否使用 `##` |
| 漫画页数没增加 | 是否在 `pages` 中列出新图片；是否上传图片 |
| 本地修改没有出现在提交列表 | 是否编辑了 D 盘旧目录，而 Desktop 打开的是 D 盘正式目录 |
| `/admin/` 无法使用 | 已填写仓库信息，但 CMS 认证尚未验证可用；先用网页或 Desktop |

日常写作无需改动 `_layouts`、`_includes`、`assets/js` 或 `.github/workflows`。旧站历史保留在备份分支中；本次已将旧笔记导入 `_posts`，主分支不再保留旧框架目录。

要撤下公开文章，可以删除对应内容文件并提交，或为文章加入 `published: false` 后提交；后者仍会保留公开源码。删除文件也不会自动抹去 Git 历史。小说、漫画需要撤下时，直接移出对应集合目录并提交；私人内容应存放在仓库之外。

本说明存放在 `docs/使用说明书.md`，`docs` 被排除在网站构建之外，因此它不会出现在博客导航中；提交后可以在 GitHub 仓库中阅读。

## 12. 发布前快速核对

1. 正在修改已连接 GitHub 的那个目录，且分支为 `master`。
2. 标题、日期、摘要和正文正确，内容可以公开。
3. 图片已经复制到仓库中，路径、大小写、漫画顺序正确。
4. 提交列表只包含本次需要的文件。
5. 已完成 Push，并确认 Actions 绿色成功。
6. 在线打开新文章或作品，检查一遍实际效果。
