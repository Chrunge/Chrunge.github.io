### 4. 💡 知识难点与场景解析 (举例说明)

#### 难点1：为什么要用 `awk` 而不是 `cut`？
*   **场景**：使用 `df -h` 查看磁盘。
    ```text
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/sda1        50G   20G   30G  40% /
    ```
*   **问题**：中间的空格数量是不固定的。
    *   如果你用 `cut -d " " -f 3`，大概率取到的是空值，因为 `cut` 认为两个空格中间有一个空字段。
    *   如果你用 `awk '{print $3}'`，`awk` 会自动忽略所有连续的空格，准确取到 `30G`。

#### 难点2：日志分析组合拳 (`sort | uniq -c | sort -nr`)
这是运维面试和实战中最常见的“连招”。
*   **场景**：Nginx 的 `access.log` 被攻击了，想找出哪个 IP 访问次数最多。
*   **命令**：
    ```bash
    awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10
    ```
*   **解析**：
    1.  `awk`：先把 IP 这一列单独拎出来。
    2.  `sort`：**必须先排序**，因为 `uniq` 只能去重相邻的行。
    3.  `uniq -c`：去重并计数（变为：`1024  192.168.1.1`）。
    4.  `sort -nr`：按计数（第一列）数值倒序排列，最大的在上面。
    5.  `head -n 10`：只看前10名“攻击者”。

> **🔐 难点解析：目录的 rwx 意味着什么？**
> *   **文件 rwx**：r=看内容，w=改内容，x=运行。
> *   **目录 rwx (概念不同)**：
>     *   `r`：能 `ls` (看文件名)。
>     *   `w`：能 `touch/rm` (在里面建/删文件)。
>     *   **`x` (关键)**：能 `cd` 进去 (进入目录)。
> *   **避坑**：如果你给一个目录 `rw-` 没有 `x`，用户是进不去的，也读不了里面的文件信息。

### 💡 运维场景·知识难点与避坑

#### 1. 软链接的“相对路径”陷阱
*   **错误做法**：`cd /app/v1; ln -s index.html link_index`
*   **后果**：当你把 `link_index` 移动到别的地方，链接就断了（红底闪烁）。
*   **正确做法**：**永远使用绝对路径**。
    `ln -s /app/v1/index.html /app/link_index`

#### 2. Rsync 的“斜杠”之谜 (面试必问)
假设源目录是 `src`，目标是 `dest`：
*   `rsync -a src dest`  👉 结果：`dest/src/...` (把目录本身拷过去了)。
*   `rsync -a src/ dest` 👉 结果：`dest/...` (把目录**里面的内容**拷过去了)。
*   **记忆法**：`src/` 里的斜杠像把盖子打开了，把东西倒出来。

#### 3. `rm -rf` 的变量灾难
*   **场景**：Shell 脚本里写 `rm -rf ${MY_PATH}/*`。
*   **灾难**：如果 `$MY_PATH` 变量因为代码逻辑没获取到（为空），命令就变成了 `rm -rf /*`。
*   **防御**：
    1.  脚本头部加 `set -u` (变量未定义则报错退出)。
    2.  写法上兜底：`rm -rf "${MY_PATH:?}/"*` (如果变量为空则报错)。

#### 4. 为什么我删了日志，磁盘空间没释放？
*   **现象**：`df -h` 看到磁盘满了，`rm log.txt` 后，`df -h` 还是满的。
*   **原因**：文件正被进程（如 Java/Nginx）占用（打开）。Linux删除原理是“引用计数”，进程没松手，文件其实还在磁盘上，只是你看不到了。
*   **解决**：
    1.  查谁在用：`lsof | grep deleted`
    2.  骚操作（不重启清空）：`echo "" > log.txt` (直接清空文件内容，而不是删除文件)。

#### 5.4 LVM 逻辑卷管理 (运维核心难点)

**概念图解**：
`PV (物理盘)` -> `VG (存储池)` -> `LV (逻辑分区)` -> `Mount (目录)`

**🔥 场景：服务器 `/data` 目录满了，插了一块新硬盘 `sdb` (100G)，如何在线扩容？**

| 步骤 | 命令 (按顺序执行) | 说明 |
| :--- | :--- | :--- |
| **1.做PV** | `pvcreate /dev/sdb` | 把生米(物理盘)洗干净。 |
| **2.查VG** | `vgs` | 查看当前卷组名 (假设叫 `centos`)。 |
| **3.扩VG** | `vgextend centos /dev/sdb` | 把新米倒进大锅(卷组)里。 |
| **4.扩LV** | `lvextend -l +100%FREE /dev/centos/data` | 把锅里新加的米全盛给 `/data` 这个碗。 |
| **5.刷FS** | **`xfs_growfs /data`** (针对 XFS)<br>**`resize2fs /dev/centos/data`** (针对 EXT4) | **最容易忘的一步！**<br>告诉操作系统空间变大了。只有执行完这步，`df -h` 才会变。 |

### 💡 深度避坑与面试题解析

#### 1. 鬼故事：磁盘满了，但我把文件删了，空间还没释放？
*   **现象**：`rm -rf /var/log/nginx/access.log` 删除了 50G 的日志，但 `df -h` 依然显示 100% used。
*   **原因**：Nginx 进程还“抓着”这个文件句柄没松手。在 Linux 中，只要文件被进程打开，即便删了文件名，磁盘空间也不会释放。
*   **解决**：
    1.  查凶手：`lsof | grep deleted`
    2.  杀进程：重启 Nginx (`systemctl reload nginx`)，空间瞬间释放。
    3.  **正确姿势**：以后别直接 `rm`，用 `echo "" > access.log` 清空内容。

#### 2. 无法卸载：`umount: /data: target is busy`
*   **新手做法**：强行拔盘或重启（危险）。
*   **高手做法**：
    ```bash
    fuser -mv /data   # 或者 lsof +D /data
    # 查出是哪个用户、哪个进程在用
    fuser -km /data   # 强行杀掉占用该目录的所有进程，然后卸载
    ```

#### 3. `fstab` 自动挂载写错导致死机
*   **风险**：`/etc/fstab` 是开机启动加载项，如果里面写错了（比如UUID不对，或者格式写错），Linux 开机就会进入 `Emergency Mode`（救援模式），远程连接直接断开。
*   **防御**：
    1.  编辑前备份：`cp /etc/fstab /etc/fstab.bak`
    2.  **编辑后必测**：执行 `mount -a`。如果没有任何报错，说明写对了，才能重启。

#### 4. 小文件把磁盘吃崩了 (Inode 耗尽)
*   **现象**：`df -h` 显示只用了 50%，但创建文件报错 `No space left on device`。
*   **排查**：执行 `df -i`，发现 Inode 使用率 100%。
*   **原因**：由于程序Bug或缓存配置不当，产生了数百万个几KB的小文件（如 session 文件、邮件队列），把“户口本”页数用光了。
*   **解决**：需要找出小文件最多的目录（通常用脚本遍历统计），然后用 `xargs` 配合删除（直接 `rm` 会报错参数过长）。
    ```bash
    # 查找当前目录下文件数量最多的子目录
    for i in ./*; do echo $i; find $i | wc -l; done
    ```

> **💡 抓包分析口诀 (TCP 三次握手)**：
> 1.  **SYN**? (客户端发起了吗？) -> 没抓到就是客户端或中间网络问题。
> 2.  **SYN+ACK**? (服务端回复了吗？) -> 没抓到就是服务端挂了或防火墙丢包。
> 3.  **ACK**? (连接建立了吗？) -> 建立了连接但没数据？那是应用层死锁。

### 💡 运维场景·知识难点与避坑

#### 1. `curl` 很慢，到底慢在哪里？
不要瞎猜是网络卡还是数据库卡，用 `curl` 的变量格式化打印时间轴：
```bash
# 创建一个 curl-format.txt 文件，内容如下：
# time_namelookup:  %{time_namelookup}\n
# time_connect:  %{time_connect}\n
# time_starttransfer:  %{time_starttransfer}\n
# time_total:  %{time_total}\n

curl -w "@curl-format.txt" -o /dev/null -s http://www.baidu.com
```
*   **解析**：
    *   `time_namelookup` 大：DNS 解析慢（换 DNS 或配 hosts）。
    *   `time_connect` 大：TCP 建连慢（网络拥堵或防火墙阻拦）。
    *   `time_starttransfer` 大：服务器处理慢（后端代码或数据库慢）。

#### 2. `0.0.0.0` vs `127.0.0.1` (新手必坑)
*   **场景**：你在服务器上启动了服务，本地 `curl localhost:8080` 通的，但同事的电脑连不上。
*   **排查**：执行 `ss -lntp | grep 8080`。
    *   显示 `127.0.0.1:8080`：**完蛋**。服务只监听了回环地址，不对外服务。需修改配置文件监听 `0.0.0.0`。
    *   显示 `0.0.0.0:8080` 或 `:::8080`：监听正确。此时不通通常是防火墙（Firewall/云安全组）问题。

#### 3. 禁 Ping 不等于不通
*   **误区**：Ping 不通就认为服务器挂了。
*   **真相**：许多云服务器默认安全组策略是禁止 ICMP (Ping) 但开放 TCP 80/22 的。
*   **操作**：一定要用 `telnet` 或 `nc -z` 测业务端口，那才是真实的连通性。

#### 4. DNS 缓存的坑
*   Linux 默认通常没有系统级 DNS 缓存（除非装了 nscd 或 dnsmasq），每次请求都会读 `/etc/resolv.conf`。
*   **修改 DNS 生效**：直接改 `/etc/resolv.conf` 文件，立即生效，不需要重启网卡。
*   **测试 DNS**：用 `dig`，不要用 `ping`（因为 ping 可能走 `/etc/hosts`，而 dig 只查 DNS）。

### 💡 运维场景·深度解析 (面试必问)

#### 1. Load Average (负载) 到底是多少算高？
*   **含义**：单位时间内，活跃（Running）+ 等待磁盘（Uninterruptible Sleep）的进程数。
*   **标准**：
    *   Load < CPU核数：系统很闲。
    *   Load = CPU核数：刚刚好（满载）。
    *   Load > CPU核数：系统过载。
*   **经验**：如果 Load 很高但 CPU 使用率很低，说明是 **IO 瓶颈**（大量的 D 状态进程在等磁盘读写）。

#### 2. 进程状态判读 (top 中的 S 列)
*   **R** (Running): 正在干活。
*   **S** (Sleeping): 睡着了，等数据（正常状态）。
*   **D** (Disk Sleep): **不可中断睡眠**。通常意味着**IO卡死**（NFS断了、硬盘坏了）。`kill -9` 杀不掉 D 状态进程，通常只能重启机器。
*   **Z** (Zombie): **僵尸进程**。父进程没给子进程收尸。僵尸不占内存不占CPU，但占 PID 号。如果看到大量 Z，说明父程序代码写得烂。

#### 3. Java 进程 CPU 飙高 100% 排查 (高频实战)
这是定位代码死循环或复杂计算的标准动作：
1.  **定位进程**：`top` 发现 PID `1001` CPU 飙高。
2.  **定位线程**：`top -H -p 1001`，发现线程 `1005` 占用最高。
3.  **转16进制**：`printf "%x\n" 1005`，得到 `3ed`。
4.  **查堆栈**：`jstack 1001 | grep -A 20 3ed`。
    *   *结果*：你就能看到是哪一行 Java 代码（如 `OrderServiceImpl.java:45`）导致了 CPU 飙高。

#### 4. 什么是 OOM Killer？
*   **现象**：MySQL 或 Java 进程突然消失了，日志里也没报错。
*   **原因**：物理内存耗尽，Linux 内核触发自我保护机制（Out Of Memory Killer），为了保住系统，选了一个占用内存最大的进程（通常是数据库）杀掉了。
*   **验证**：`dmesg | grep -i "out of memory"` 或 `grep "OOM" /var/log/messages`。

## 8. 系统监控与性能分析 (全链路排查)

**前置准备**：大部分高级命令（iostat, mpstat, sar, pidstat）都在 `sysstat` 包里。
> 安装：`yum install -y sysstat` 或 `apt install sysstat`

#### 8.1 宏观全局概览 (第一眼看什么)

登录服务器后的前 30 秒，决定了你排查的方向。

| 命令 | 功能 | 关键指标 | 实战解读 |
| :--- | :--- | :--- | :--- |
| **top** | 综合监控 | **Load Avg** (右上角)<br>**%CPU** (wa, si, st) | **系统卡不卡看 Load**：如果 1分钟Load > CPU核数，说明堵车了。<br>**卡哪里看 CPU行**：`wa`高=硬盘慢；`us`高=代码慢。 |
| **htop** | **(推荐)** 增强版Top | 条形图、颜色区分 | 比 top 更直观，支持鼠标点击列头排序，能直接选进程 Kill。 |
| **uptime**| 仅看负载 | Load Average | 极简模式，不想被 top 刷屏时用。 |
| **dstat** | **全能监控** (神器) | CPU/Disk/Net/Page | **`dstat -cmdng 1`** <br> *(一行显示 CPU、内存、磁盘读写、网络流量。取代 vmstat/iostat 的现代工具)* |

#### 8.2 CPU 维度深入 (算力瓶颈)

如果 `top` 里 CPU 使用率很高，用这些工具查细节。

| 命令 | 功能 | 常用选项 | 实战场景 & 难点 |
| :--- | :--- | :--- | :--- |
| **mpstat** | **多核**分析 | `-P ALL 1` | **查单核打满**：<br>总 CPU 使用率可能只有 10%，但某一个核 100%，导致单线程程序卡死。 |
| **pidstat**| **进程**细分 | `-u 1 -p [PID]` | **查谁在吃 CPU**：<br>当你知道是哪个 PID 之后，用这个看它是用户态(`%usr`)高还是内核态(`%system`)高。 |
| **sar** | **历史**记录 | `-u` (看CPU)<br>`-f /var/log/sa/saxx` | **查昨晚的故障**：<br>`top` 只能看现在，`sar` 能回溯历史数据（如：昨天凌晨3点 CPU 是多少）。 |

> **🔥 CPU 关键指标详解 (top 第三行)**：
> *   `us` (User): 用户程序（Java/Nginx）在忙。 -> **优化代码**。
> *   `sy` (System): 内核在忙（驱动/系统调用）。 -> **查驱动或频繁上下文切换**。
> *   `wa` (IO Wait): CPU 在等硬盘。 -> **查磁盘 I/O**。
> *   `si` (Soft IRQ): **软中断**。通常是**网络流量过大**导致 CPU 忙着处理网卡中断。
> *   `st` (Steal): **偷取时间**。仅在虚拟机/云主机可见。如果这个高，说明**宿主机（云厂商）超卖了**，资源被隔壁邻居抢了。

#### 8.3 内存维度深入 (容量瓶颈)

| 命令 | 功能 | 常用选项 | 实战场景 & 难点 |
| :--- | :--- | :--- | :--- |
| **free** | 内存概览 | `-h` | **看 `available`**：这才是真实可用内存。<br>**看 `buff/cache`**：如果很高但 available 够用，**是正常的**（Linux 特性）。 |
| **vmstat** | 虚拟内存 | `1` (每秒刷新) | **必看 `si` / `so`** (Swap In/Out)：<br>如果这两个数**长期非 0**，说明物理内存不够了，系统在频繁读写 Swap 分区，**机器会极卡**。 |
| **slabtop**| 内核内存 | `-s c` | **高级排查**：<br>如果 `free` 显示内存耗尽，但进程都没怎么用内存，可能是大量小文件导致 **Slab (内核缓存)** 泄漏。 |

> **💡 知识难点：Buffer vs Cache**
> *   **Buffer (缓冲)**：给**写**操作加速（把零散的写入攒一波再写进硬盘）。
> *   **Cache (缓存)**：给**读**操作加速（把读过的文件存在内存里，下次读就不用查硬盘）。
> *   **手动释放**：`echo 3 > /proc/sys/vm/drop_caches` (生产环境慎用，可能导致瞬间 IO 飙高)。

#### 8.4 磁盘 I/O 维度深入 (存取瓶颈)

当 `top` 中 `%wa` 高时，进入此环节。

| 命令 | 功能 | 常用选项 | 实战场景 & 难点 |
| :--- | :--- | :--- | :--- |
| **iostat** | IO 统计 | `-x 1` | **看 `%util`**：接近 100% 说明硬盘忙疯了。<br>**看 `await`**：请求平均等待时间。SSD 通常 < 1ms，机械盘 < 10ms。如果 > 20ms，说明磁盘响应极慢。 |
| **iotop** | 抓进程 | `-o` (只显示活跃) | **抓凶手**：<br>一眼看到是哪个进程在疯狂 Read/Write。 |
| **pidstat**| 进程IO详情 | `-d 1` | 如果没装 `iotop`，用这个也能看每个进程每秒写了多少 KB。 |

#### 8.5 网络流量维度深入 (带宽瓶颈)

| 命令 | 功能 | 常用选项 | 实战场景 |
| :--- | :--- | :--- | :--- |
| **iftop** | 实时流量监控 | `-n` (不解析域名) | **可视化监控**：<br>能看到本机在和**哪个 IP** 进行传输，进度条显示占用了多少带宽。 |
| **sar** | 网卡历史 | `-n DEV 1` | **查看数据包量**：<br>关注 `rxpck/s` (每秒收包数)。如果带宽没满，但包量巨大（几十万），可能是 **DDoS 攻击**或**小包风暴**。 |
| **netstat**| 协议栈统计 | `-s` | **查丢包**：<br>`netstat -s | grep -i drop`，查看是因为缓冲区满丢包，还是防火墙丢包。 |

#### 8.6 内核日志 (最后的黑匣子)

当系统没有任何指标异常，但进程莫名消失或系统重启时。

| 命令 | 功能 | 实战场景 |
| :--- | :--- | :--- |
| **dmesg** | 打印内核环形缓冲区 | `dmesg -T | tail -n 20`<br>**查 OOM**：`dmesg | grep -i "killed"` (看是不是内存溢出杀进程了)<br>**查掉盘**：`dmesg | grep -i "I/O error"` |
| **/var/log/messages** | 系统主日志 | CentOS看这个，Ubuntu看 `/var/log/syslog`。<br>结合时间点查看系统发生了什么。 |

### 💡 运维排查思维导图 (Brain Tattoo)

当有人喊“系统挂了/慢了”，请按 **USE 方法** (Utilization, Saturation, Errors) 顺序排查：

1.  **负载高吗？** (`uptime`)
    *   **高** -> 往下查。
    *   **低** -> 可能是网络不通，或应用死锁（不耗资源但就是不动）。

2.  **是谁高的？** (`top`)
    *   **`us` 高** -> 程序在算（查代码）。
    *   **`sy` 高** -> 内核在忙（查驱动/系统调用）。
    *   **`wa` 高** -> **硬盘慢**（转步骤 3）。
    *   **`si` 高** -> **软中断**（查网卡流量/PPS）。

3.  **硬盘在干嘛？** (`iostat -x 1` + `iotop`)
    *   `%util` 100% -> 硬盘满载。
    *   `await` 高 -> 硬盘响应慢（可能是坏道或云盘抖动）。

4.  **内存够吗？** (`free -h` + `vmstat 1`)
    *   `available` 小 + `si/so` 动了 -> **内存不足，正在吃 Swap，系统必卡**。

5.  **网络满吗？** (`iftop`)
    *   带宽打满 -> 业务高峰或被攻击。
    *   带宽没满但卡 -> 查丢包 (`ping` / `netstat -s`)。

6.  **啥都正常但就是崩了？**
    *   **看日志**：`dmesg` 查 OOM Killer，`tail -f error.log` 查应用报错。

### 💡 运维避坑与黑科技

#### 1. 历史记录的“隐身术”
*   **场景**：你需要执行一条带明文密码的命令 (如 `mysql -p123456`)，但不想被 `history` 记录下来被别人看到。
*   **操作**：在命令最前面**加一个空格**。
    ```bash
     mysql -u root -p123456  # 注意最前面的空格
    ```
    *注：需确保环境变量 `HISTCONTROL` 包含 `ignorespace` (默认通常都有)。*

#### 2. `wget` 下载慢/断开
*   不要傻傻地重头下载。使用 `wget -c URL` (Continue)，它可以从断开的地方接着下。

#### 3. 为什么我的 `crontab` 时间不对？
*   **现象**：`date` 命令看时间是 10:00 (CST)，但日志里打印的是 02:00。
*   **原因**：你可能只改了**显示时间**，没改**时区**。或者有些服务（如 Java, MySQL）启动时读取了旧时区，改完系统时间后**必须重启服务**才能生效。

#### 4. 防止手滑覆盖文件
*   新手最容易犯的错：本想追加日志 `>>`，结果写成了覆盖 `>`，导致原文件清空。
*   **防御**：在生产环境谨慎使用重定向符号。可以用 `tee -a` 命令替代 `>>`，更直观。
    ```bash
    echo "content" | tee -a config.txt
    ```

## 12. 现代运维补充包 (必会技能)

#### 12.1 服务管理 (Systemd) — 系统的管家

**核心概念**：
*   **Unit File**: `/usr/lib/systemd/system/nginx.service` (服务的配置文件)。
*   **关键动作**：当你修改了 service 文件，必须执行 **`systemctl daemon-reload`**，否则修改无效。

| 命令 | 功能 | 常用选项 | 实战举例 |
| :--- | :--- | :--- | :--- |
| **systemctl** | 服务控制 | `status` : 看状态<br>`start/stop` : 启停<br>`restart` : 重启<br>`enable` : **设置开机自启** | **`systemctl enable --now nginx`** <br> *(最强组合拳：设置为开机自启，并且立刻启动它)*<br>`systemctl list-unit-files \| grep enabled` <br> *(查查哪些服务是开机自启的)* |
| **journalctl**| **查服务日志**<br>(取代 message) | `-u` : 指定服务<br>`-f` : 实时监控<br>`--since` : 按时间过滤 | **`journalctl -u nginx -f`** <br> *(实时看 nginx 标准输出日志)*<br>`journalctl -u sshd --since "10 min ago"` <br> *(查最近10分钟谁登录过)* |

> **💡 避坑指南**：
> 服务启动失败时，`systemctl status` 显示的信息往往不全。
> **必杀技**：直接运行 `journalctl -xe` 或 `journalctl -u 服务名 -n 50` 查看详细堆栈报错。

#### 2. 内核参数调优 (Sysctl)
当服务器并发量上来后（如 Nginx 处理 10万+ 连接），默认的 Linux 配置会成为瓶颈。

| 命令 | 功能 | 配置文件 | 实战操作 |
| :--- | :--- | :--- | :--- |

> **实战配置 Nginx 日志轮转**：
> 在 `/etc/logrotate.d/nginx` 中配置 `daily` (每天切)、`rotate 7` (保留7天)、`compress` (压缩)。

### 💡 终极避坑：关于 `/proc` 目录

你可能会看到很多教程让你 `cat /proc/cpuinfo` 或 `cat /proc/meminfo`。

*   **本质**：`/proc` **不是真实的硬盘目录**，它是内存的映射，是内核暴露给用户的窗口。
*   **操作禁忌**：**严禁** 对 `/proc` 目录下的文件执行 `rm` (删除) 或 `mv` (移动) 操作！这可能会导致内核崩溃。
*   **正确用法**：只能 `cat` (看) 或 `echo` (修改内核参数)。
    *   *例*：`echo 1 > /proc/sys/net/ipv4/ip_forward` (开启路由转发)。
